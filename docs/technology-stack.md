# Технологический стек

## 1. Цель документа

Документ фиксирует технологии, на которых будет построена первая версия FPV Operator Trainer.

Первая версия включает:

- веб-интерфейс оператора;
- четыре диагностических модуля;
- только первый уровень сложности каждого модуля;
- сохранение попыток и результатов;
- просмотр базовой истории прохождений.

## 2. Общая архитектура

Приложение строится как клиент-серверная система из трёх основных частей:

```text
React-приложение
       │
       │ HTTP / JSON
       ▼
FastAPI API
       │
       │ SQL
       ▼
PostgreSQL
```

Фронтенд не обращается к базе данных напрямую. Все операции выполняются через API бэкенда.

## 3. Бэкенд

### Основные технологии

| Технология | Назначение                                                    |
| -------------------- | ----------------------------------------------------------------------- |
| Python               | Основной язык бэкенда                                |
| FastAPI              | HTTP API и бизнес-логика                                   |
| Pydantic             | Проверка входных и выходных данных API    |
| SQLAlchemy           | Работа с PostgreSQL через ORM                               |
| Alembic              | Версионирование структуры базы данных |
| Uvicorn              | ASGI-сервер для локальной разработки        |

### Почему FastAPI

- хорошо подходит для типизированного JSON API;
- автоматически формирует документацию OpenAPI;
- использует Pydantic для строгой проверки данных;
- поддерживает асинхронную обработку запросов;
- позволяет писать модульные и легко тестируемые обработчики.

### Формат API

На первом этапе используется REST API с JSON. Предварительный префикс маршрутов:

```text
/api/v1
```

WebSocket и GraphQL в первой версии не требуются.

## 4. База данных

### Основные технологии

| Технология | Назначение                                           |
| -------------------- | -------------------------------------------------------------- |
| PostgreSQL           | Постоянное хранение данных             |
| asyncpg              | Асинхронный драйвер PostgreSQL для Python |
| Alembic              | Создание и применение миграций      |

### Какие данные хранятся

- пользователи или операторы;
- диагностические модули;
- доступные уровни сложности;
- попытки прохождения;
- время начала и завершения попытки;
- количество правильных и ошибочных действий;
- итоговый результат;
- технические события, необходимые для последующего анализа попытки.

Случайно сгенерированное задание конкретной попытки также сохраняется. Это позволит воспроизвести расчёт результата и проверить его корректность.

### Что не используется

SQLite не используется как отдельная среда разработки. Локальная и рабочая среды должны работать с PostgreSQL, чтобы избежать различий в поведении базы данных.

## 5. Фронтенд

### Выбранный стек

| Технология | Назначение                                                                 |
| -------------------- | ------------------------------------------------------------------------------------ |
| React                | Компонентная модель интерфейса                           |
| TypeScript           | Типизация клиентского кода                                   |
| Vite                 | Сборка и локальный сервер разработки                 |
| React Router         | Маршрутизация между экранами                               |
| TanStack Query       | Запросы к API, кеширование и состояния загрузки |
| Tailwind CSS         | Система стилей на основе дизайн-токенов            |
| shadcn/ui            | Базовые доступные UI-компоненты                            |
| Lucide React         | Единый набор интерфейсных иконок                        |

### Почему React + TypeScript

- подходит для интерактивных тестов с большим количеством состояний;
- позволяет разделить интерфейс на переиспользуемые компоненты;
- TypeScript снижает число ошибок при обмене данными с API;
- экосистема содержит готовые решения для маршрутизации, форм и тестирования;
- приложение можно развивать без смены базового фронтенд-стека.

### Работа со стилями

Интерфейс не будет разрабатываться на чистых HTML и CSS. В качестве основы используются React-компоненты, Tailwind CSS и shadcn/ui.

В проекте будут определены общие дизайн-токены:

- цвета;
- типографика;
- отступы;
- радиусы;
- размеры интерактивных элементов;
- состояния наведения, фокуса, ошибки и успешного выполнения.

Точечный CSS допускается только там, где Tailwind недостаточен: сложная анимация, нестандартная сетка диагностического задания или специфичная визуализация.

### Управление состоянием

На первом этапе отдельная глобальная библиотека состояния не требуется:

- серверные данные управляются через TanStack Query;
- локальное состояние заданий хранится в React-компонентах и специализированных хуках;
- состояние, которое должно пережить обновление страницы, сохраняется через API.

Если позднее появится сложное глобальное состояние, можно добавить Zustand без изменения основной архитектуры.

## 6. Контракт между фронтендом и бэкендом

FastAPI формирует OpenAPI-схему. На её основе для фронтенда генерируются TypeScript-типы и API-клиент.

Это обеспечивает:

- единый формат запросов и ответов;
- проверку несовместимых изменений;
- отсутствие ручного дублирования моделей данных;
- автодополнение типов во фронтенде.

Рекомендуемый генератор клиента — `openapi-typescript`.

## 7. Тестирование

### Бэкенд

- pytest — модульные и интеграционные тесты;
- HTTPX — тестирование FastAPI-маршрутов;
- отдельная тестовая база PostgreSQL — проверка запросов и миграций.

### Фронтенд

- Vitest — модульные тесты;
- React Testing Library — тестирование компонентов и пользовательских действий;
- Playwright — сквозные сценарии прохождения модулей через браузер.

### Обязательные сквозные сценарии первой версии

1. Запуск и завершение первого модуля.
2. Запуск и завершение второго модуля.
3. Запуск и завершение третьего и четвёртого модулей.
4. Сохранение результата в PostgreSQL.
5. Восстановление незавершённой попытки после обновления страницы.
6. Отображение истории результатов оператора.

## 8. Локальная разработка и развёртывание

Для локальной разработки используется Docker Compose:

```text
frontend    React + Vite
backend     FastAPI + Uvicorn
database    PostgreSQL
```

Переменные окружения хранятся в `.env`-файлах, а пример безопасных настроек — в `.env.example`. Секреты и реальные пароли не добавляются в Git.

Для первой рабочей версии предполагается контейнерное развёртывание:

- собранный фронтенд раздаётся веб-сервером;
- FastAPI работает отдельным контейнером;
- PostgreSQL использует постоянный том;
- миграции Alembic выполняются перед запуском новой версии бэкенда.

## 9. Структура репозитория

Планируемая структура:

```text
fpv_operator_trainer/
├── backend/
│   ├── app/
│   ├── migrations/
│   └── tests/
├── frontend/
│   ├── src/
│   └── tests/
├── docs/
├── docker-compose.yaml
└── README.md
```

Бэкенд и фронтенд находятся в одном репозитории. Для текущего масштаба это упрощает согласование API, локальный запуск и выпуск версий.

## 10. Зафиксированные решения

| Область                        | Решение                                    |
| ------------------------------------- | ------------------------------------------------- |
| Бэкенд                          | FastAPI на Python                               |
| База данных                 | PostgreSQL                                        |
| ORM и миграции               | SQLAlchemy + Alembic                              |
| Фронтенд                      | React + TypeScript                                |
| Сборка фронтенда       | Vite                                              |
| UI и стили                      | Tailwind CSS + shadcn/ui                          |
| Запросы к API                 | TanStack Query                                    |
| API                                   | REST + JSON + OpenAPI                             |
| Локальное окружение | Docker Compose                                    |
| Тестирование              | pytest, Vitest, React Testing Library, Playwright |

Версии библиотек будут зафиксированы lock-файлами при создании приложений. До начала реализации не следует указывать номера версий вручную: выбираются актуальные совместимые стабильные версии на момент инициализации проекта.
